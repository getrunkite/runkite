# Advisory agent capability descriptors

Status: implemented in v0.10.0. Published v0.9.0 did not bootstrap
this descriptor. It adds no migration, runner protocol message, permission or
runtime feature.

The control plane writes a stable `capabilities.runkite_profile` object when it
bootstraps configured agents. Agent Detail and Try Agent render it as an
advisory description of the configured framework profile. They retain unknown
values rather than infer support from a runner dispatch name.

## What the descriptor establishes

`schema_version: 1` identifies this format. `provenance` is
`control_plane_configuration`, and `framework_kind` comes from the configuration's
framework kind before any execution-pool routing. `execution_boundary` is
`direct_profile` or `execution_pool`.

This source has inspected descriptions for the direct `python-langgraph`,
`typescript-langgraphjs`, `typescript-ai-sdk`, `python-agent-framework`,
`python-openai-agents`, `python-pydantic-ai` and `python-google-adk` profiles.
Other kinds, including older checkout-only adapters and custom kinds, have
unknown features. All execution-pool combinations also remain unknown in this
first version. A name that resembles a known framework is insufficient.

The fields describe conditional adapter behavior:

- `native_resume` and `checkpoint_ref` are `langgraph_checkpoint_required` for
  the two LangGraph profiles. A usable checkpoint, saver mode and compatible
  thread identity are still required. The five managed SDK profiles mark these
  operations `unsupported`; plane connector approval remains independent.
- `continuity` is `langgraph_checkpoint_state` for LangGraph. The actual saver
  might be direct Postgres, HTTP proxy or ephemeral memory. It is
  `successful_turn_state_http` for the five managed SDK profiles, which require
  the opaque HTTP API and commit successful-turn history or session state.
  This does not restore unfinished turns or supply native interrupt resume.
- `local_tool_allowlist` is `langgraph_stream_names` for observed graph tool
  calls, or `adapter_local_functions` for the supported SDK local-function
  paths. Both require an explicitly configured `allowed_tools` list. Neither
  describes arbitrary code or replaces connector policy, grants or argument
  predicates. Absence of an allowlist is not a deny-all declaration.
- `schema_reporting` is `static_graph_introspection` for static Python
  LangGraph graphs. Factories and missing/failed reports retain bootstrap
  stubs. The other described profiles use `bootstrap_stub`. This field does
  not report whether schema publication succeeded or whether a separately
  supplied schema is current.

The v0.10.0 [publication-recovery task](schema-publication-recovery.md) does
not add a descriptor value or a readiness signal. It fills only exact bootstrap
rows from cached static Python reports; useful/partial reports can remain from
another worker. The existing `schema_reporting` condition and unknown freshness
are unchanged.

Unknown features use the literal `unknown`. The UI also treats missing,
malformed or future descriptor formats and unfamiliar feature codes as unknown.
It uses fixed local support links, never URLs supplied in capability metadata.

## Evidence and ownership boundaries

This is a configuration snapshot generated by the control plane. It is not a
runner observation, worker lease, readiness result, code attestation or sandbox
proof. It says nothing about a particular graph being loaded, checkpoint
availability, provider credentials or effective runner environment. Capability
metadata is not an authorization source, and the UI does not gate requests with
it. Try Agent can still submit the same requests as before.

Relevant inspected implementation paths are:

- `python/runkite_runner/worker.py`: `build_run_config`, `execute_run` and the
  observed-tool name filter; `checkpoint.py`: `CheckpointManager`;
  `schema_introspect.py`: `report_agent_schemas`.
- `typescript/runkite-runner/src/executeRun.ts`, `checkpoint.ts` and
  `langGraphExecution.ts`: resume, checkpoint selection, observed-tool names
  and saver attachment.
- `typescript/runkite-runner/src/aiSdkAdapter.ts`: native resume/checkpoint
  refusal, local execute wrappers and committed-turn state.
- `python/adapters/{agent_framework,openai_agents,pydantic_ai,google_adk}_adapter/adapter.py`:
  native resume/checkpoint refusal, run-bound HTTP state and local-function
  middleware/hooks/callbacks. Google ADK retains session-local state; this is
  not a claim of shared app/user state support.

The descriptor itself adds no registry manifest, dependency installer, graph
editor, runtime probe or dynamic framework introspection. The separate optional
[catalog requirements convention](../registry.md#optional-definition-requirements-unreleased-convention)
is publisher-supplied metadata, displayed read-only as escaped JSON. It neither
changes this descriptor nor verifies compatibility or grants authority.

## Preservation and versioning

Bootstrap reads the existing agent before replacing its configured definition.
It preserves opaque capability keys outside `runkite_profile` and unknown keys
inside a descriptor object. The reserved fields listed above are regenerated;
a malformed non-object value at that reserved key is replaced. A failed read
skips that agent's registration rather than erase unread capabilities.

Adding these fields to an existing agent creates one ordinary new definition
version. There are no timestamps or probe results in the descriptor, so an
unchanged restart does not create another version. Changing the configured
profile updates its known fields through the existing version history. Old
snapshots stay immutable. Existing loaded-value replacement semantics remain;
this read/merge/write does not add concurrent-edit protection. Upgrade all
control-plane replicas before relying on preservation because older bootstrap
code still writes an empty capabilities object.

The focused bootstrap tests exercise the actual SQLite version store, opaque
key preservation, unchanged restarts, profile changes and failed reads. UI
helper tests cover unknown formats/profiles/pools, fixed guide selection and
exact tenant/agent selection. These checks qualify the descriptor handling,
not native execution of each framework.
