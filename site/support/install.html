Install

Choose a local demo, a production-shaped Compose stack, or Kubernetes/Helm. Postgres + Redis are the Supported HA backend pair. Complete that production profile with client authentication, kind-scoped runner tokens and tenant allowlists, TLS and your normal operational controls.

Choose the component you need

Upgrading to v0.10.0: stop submissions and cron dispatch, drain assignments and stop all writers. Verify restorable database, queue and receipt backups, apply Postgres/SQLite migration 23 or MySQL migration 24, and deploy matching protocol-1 planes and runners. Reconcile legacy accounting, hook claims and ambiguous receipts before restoring traffic. Follow the complete coordinated upgrade; replacing only a runner or an image is insufficient.

Runkite publishes one control-plane binary, two Python packages, two npm packages and three container images. Start with a control plane, then choose runners or decision helpers for your application. Binary and container forms are deployment alternatives.

Choose the execution boundary: managed agents use a runner; apps that keep their own loop can use a decision helper. The helpers are independent of the runner packages. A Node runner does not require the JavaScript governance helper. Both paths connect to your self-hosted control plane; an app-owned decision creates no managed Thread or Run.

The Helm chart is installed from the repository, not a published chart registry. Framework extras are options on the Python package, not additional PyPI projects. The managed chat UI bridge and runnable examples remain checkout assets. OpenAPI specifications are attached to GitHub Releases. See SDK integration contracts for framework dependencies and capabilities. The Go binary is the server, not a separate Go client SDK.

Option 1: laptop demo (5 minutes, not for anything real)

git clone https://github.com/getrunkite/runkite.git && cd runkite
docker compose -f docker-compose.dev.yml up -d --build

This starts the plane, a Python runner and the fake bank MCP service. It uses SQLite in the plane container and an in-process queue, with no client authentication. The queue is process-local; the SQLite file is not backed by a named volume and is lost when that container is recreated. This profile is intentional: it's for kicking the tires and following First agent, not for anything you'd point real traffic at. If you just want to see it work without cloning anything, use Try it instead, same idea, zero setup.

Option 2: Supported profile (Postgres + Redis)

This stack uses the backend pair covered by the multi-replica Compose proof. It is a local wiring example until you add client authentication and TLS. Postgres holds every agent/thread/run/audit record across replicas, and Redis supplies the shared queue, event broker and cancellation path. Attempt fencing protects durable run completion during reclaim. External tool writes still need downstream idempotency; these backends do not make arbitrary side effects exactly once.

Steps:

  1. cp .env.example .env
    Open .env and fill in two values: a generated POSTGRES_PASSWORD and RUNNER_TOKEN (generate one with openssl rand -hex 32). Both are required, the stack refuses to start with a placeholder or empty value instead of silently booting with a well-known default password. 
  2. docker compose up -d --build
    This starts five services: Postgres, Redis, the control plane, a Python runner loading the bundled agents, and the fake bank MCP service. 
  3. curl -sf http://localhost:2026/readyz && echo OK
    /readyz doesn't just check that the HTTP server is up, it actually verifies Postgres and Redis are reachable. If this returns anything other than OK, check docker compose logs runkite before assuming your agent config is the problem.
  4. Open http://localhost:2026/admin/ to confirm the plane sees the bundled example agents (see Admin UI guide for what you'll find there).

Client-facing auth is not turned on by this compose file. It sets RUNKITE_ALLOW_INSECURE_SERVE=1 specifically so the demo boots without you having to write an auth config first, this is fine on your own machine, but before this stack is reachable from anywhere else, add a real auth section to langgraph.json (see Admin login for the exact shape) and remove that env var. Without auth configured, RUNKITE_ALLOW_INSECURE_SERVE is required, the plane refuses to boot in an ambiguous "maybe secure" state.

Option 3: Kubernetes / Helm

Same Postgres + Redis topology, packaged as a Helm chart under deploy/helm/runkite. Unlike the Compose demo above, the chart's default config does wire in real client auth out of the box, you supply the API key value, not a bypass flag.

  1. Have a Postgres and Redis reachable from the cluster, the chart does not bundle them; point it at infrastructure you already run.
  2. helm upgrade --install runkite deploy/helm/runkite \
  -f deploy/helm/runkite/values.yaml \
  -f deploy/helm/runkite/values-supported.yaml \
  --set secrets.postgresDsn="postgres://..." \
  --set secrets.redisUrl="redis://..." \
  --set secrets.apiKey="$(openssl rand -hex 32)"
  3. Optional: add -f deploy/helm/runkite/values-tls.yaml for pod-to-pod TLS/mTLS between the control plane and runners.
  4. Check rollout: kubectl get pods -l app.kubernetes.io/name=runkite, then port-forward or hit your Ingress's /readyz.

Kubernetes packaging itself has been proven with kind (install, runner token rotation, mid-run reclaim, and Ingress/NetworkPolicy, run the whole suite with make kind-helm-all) and with a named smoke test on real EKS (install, a real run, and a control-plane pod kill recovering cleanly, see k8s-eks-soak-results.md). What's not proven yet on cloud Kubernetes is a long, multi-availability-zone HA soak, the Compose multi-replica soak is still the deeper correctness proof today. Until that longer cloud soak exists, treat a Kubernetes install as "packaging and day-1 ops are solid" rather than "identical HA guarantees to Compose."

Package and upgrade boundaries

Registry installs follow the latest tagged release. The v0.10.0 packages use Apache-2.0 and include LangGraph defaults and the optional TypeScript AI SDK backend (--framework ai-sdk). The Python wheel also packages managed Microsoft, OpenAI Agents, Pydantic AI and Google ADK adapters: install the matching optional extra and dedicated command. The stock Python image does not install these optional SDKs. Governance helpers (createGovernedExecute, optional Microsoft function middleware) are separately published as runkite-governance on npm and PyPI starting with v0.8.0. See the integration guide.

Install the separate runkite-governance helper with npm install runkite-governance or python -m pip install runkite-governance. See decision-helper installation and boundaries. The managed application UI bridge remains a checkout example, not another published SDK.

v0.8.0 upgrade: use the identity and usage guide for the coordinated SQL migration, runner HTTPS requirements and opt-in ownership rollout. Independent external assessment remains pending.

v0.7.0 upgrade: select matching plane and runner artifacts and pin image tags explicitly. New authority fields require a coordinated SQL upgrade with no mixed-version writers. See Security operations and upgrade requirements.

Custom or older runners must echo the assignment's exact generation on run-specific RPCs and bound HTTP calls. Generation 0 is not a wildcard for a later attempt. Runner tokens are bound to their kind. Upgrade and test custom runners with the plane before replacing production replicas.

What to expect

  • "/readyz never turns healthy.": almost always Postgres or Redis isn't reachable yet, or the DSN/URL is wrong. Check docker compose logs / pod logs for the exact connection error before touching anything else.
  • "serve refuses to start.": this is usually intentional, not a bug: production admission checks fail closed on an insecure combination (e.g. runner tokens configured but no matching RUNNER_TENANTS_*). The startup log names exactly which check failed.
  • Required secrets fail loudly, not silently: an unset POSTGRES_PASSWORD/RUNNER_TOKEN stops the stack from starting at all, instead of quietly deploying with a shared default password everyone forgets to change.
