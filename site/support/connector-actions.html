Govern

Connector actions

Follow a managed MCP tool request from its policy decision to dispatch intent and the response Runkite could observe.

Availability: v0.7.0 candidate source (not published). Rebuild the control plane from this source to use these settings and screens. Published v0.6.1 binaries do not implement them. Capture is off by default and requires Postgres, MySQL or SQLite.

Enable recording

Add these settings to the existing policy block in your control plane's first langgraph.json. Keep your current grants, predicates and approval rules.

{
  "policy": {
    "audit_required": true,
    "action_evidence": true
  }
}

This fragment is not an allow rule. Existing policy decides which calls can proceed. Required audit must stay enabled; startup rejects incompatible configuration or a store without SQL action support. Follow the upgrade procedure before enabling capture consistently on every replica.

Upgrade assigns a distinct insertion identity to each existing run. This backfill writes stored rows and can take time on large databases. Plan a maintenance window, a verified backup and database log capacity; stop all writers until it completes. Old managed approvals are not retroactively bound to current runs and require fresh review. Decision-only approvals retain their existing namespace.

Approval upgrade: managed connector approvals belong to the original stored run incarnation and configured connector target revision, including when capture is off. Historical approvals missing either binding remain audit records and require a new submission and fresh review. A replacement run cannot inherit an old approval by reusing its run ID and generation. Admin and Review mark unsupported bindings Fresh review required and disable Approve; Deny remains available for pending rows. Standalone decision approvals keep their separate expiring namespace and do not need a managed run or connector target.

The scope is managed connector tools/call, for both JSON and negotiated streamable HTTP. Local framework tools, model calls and the app-owned decision API are outside this history. The decision API still creates no managed Thread or Run. Incoming calls to Runkite's public /mcp agent interface are a separate direction; this recorder follows outgoing gated tool attempts inside managed runs.

Inspect an attempt

  1. Open Admin → Connector actions. Filter by tenant, run, connector or state. Run Detail also shows recent attempts for that exact run incarnation.
  2. Open an action to see its original generation, argument digest, recorded policy effect, final authorization source and ordered observations.
  3. Use the separate approval reference to inspect all approval statuses. An action ID identifies a request attempt; a pending approval ID identifies a one-shot capability.
  4. Use X-Runkite-Connector-Action-Id from the tool response to find a particular attempt. Existing policy audit and policy exports carry connector_action_id for correlation.

Admin remains globally privileged. Filters are not tenant-scoped reviewer permissions. Archived actions remain readable when their run is pruned; run navigation is offered only for a verified matching incarnation. An incomplete event list is labeled. Background refresh is bounded; use Refresh when it stops.

Read the states precisely

  • Received: the attempt identity was saved; no dispatch evidence yet.
  • Blocked: policy refused this attempt.
  • Approval required: this request waited for review. Approving does not execute it. A matching retry creates a separate attempt.
  • Ready: the decision permits preparation; no dispatch intent is committed yet.
  • Not dispatched: this recorder's protected call did not reach its send boundary. Protocol discovery or credential preparation may still have contacted an upstream.
  • Dispatch intent: authorization and intent committed before sending. It does not prove delivery or an external effect.
  • Response observed: a complete correlated protocol response was observed. Inspect its kind, HTTP status and RPC error code. This includes error responses and does not prove business success.
  • Outcome unknown: dispatch was authorized but a trustworthy complete outcome was unavailable. The tool may have executed.

Policy and authority remain separate: an original pending decision can use a matching approved capability. An original deny requires an audited break-glass window; approval cannot override it. Missing policy, tool or credential revisions mean that revision was unavailable, not that its value was verified. Historical actions can also lack a target revision.

Read the configured target revision

New managed actions record target_revision, a versioned SHA-256 digest of the configured MCP endpoint, transport, auth identity/reference, scopes, tool filters and optional nonsecret mcp.revision. Resolved secret values are excluded. One request uses a pinned configuration snapshot from policy evaluation through dispatch; matching approval consumption requires that same revision.

This proves which configured target the attempt used. It does not prove an upstream tool's implementation, schema or business effect, nor the configuration of every replica. Admin and Review display the stored revision; the server checks its current target when approving and executing. See target-bound approvals for configuration changes and fresh-review requirements.

Investigate an unknown outcome

  1. Save the action ID, tenant, run and original generation. Check the timeline, linked approval and trace correlation.
  2. Inspect the configured target's own records or business idempotency key to determine whether it committed the operation. A transport error, HTTP error or cancelled run cannot establish that.
  3. Restore SQL availability if evidence persistence failed. Expired intents become unknown through metadata reconciliation; a late original response can still be recorded.
  4. Retry only when your application's business rules and target-side idempotency make it safe. Runkite never retries a protected tool to fill missing evidence. A new action ID does not deduplicate an external effect.

A rolled-back prepare leaves approval authority unconsumed and blocks the protected call. A lost database commit acknowledgement can leave intent and consumed approval even though the callback does not send the tool request, so inspect both before retrying. After dispatch intent, an evidence or connection failure can also return an error even if the external service executed the tool. An error alone does not establish a safe retry.

Retention and privacy

Action history has independent retention. Run or thread pruning does not delete it. Retention is disabled by default; this optional fragment prunes resolved evidence older than 30 days:

{
  "retention": {
    "connector_actions_max_age": "720h"
  }
}

Only old blocked, not-dispatched and response-observed records are pruned, with their events. Unresolved attempts, pending review, intents and unknown outcomes remain. Earlier pending attempts can stay in that state after a later retry consumes the approval, so retention does not guarantee bounded storage. Plan backups, archival and capacity accordingly.

New action records contain typed metadata, not raw arguments, result bodies, credentials, endpoint URLs or provider error text. Principal, identifiers, digests and trace IDs are still sensitive. Existing policy audit has its own capped, redacted argument display and retention. This action trail is not a vault or implementation verifier. Separate unreleased registered database leases and durable action export extend it under explicit lifecycle contracts.

API and design

Read-only Admin endpoints: GET /admin-api/connector-actions and GET /admin-api/connector-actions/{actionID}. Both require Admin authority when authentication is configured and return 501 on stores without action support. Lists use bounded pages and X-Next-Cursor; detail includes the action, ordered events and whether its original run remains available.

Tenant Review workspace (unreleased)

The v0.7.0 candidate (not published) adds primary governance:read and governance:approve roles for a verified tenant. Reviewers use a separate workspace and API; they gain no global Admin or conversation access. Read-only metadata excludes argument displays, while approvers keep the existing redacted review view. See Tenant review for setup, absolute session expiry, API scope and rollout.

Approval, credential and export references (unreleased)

Current source populates configured policy and optional observed tool-schema identities. A credential reference from the registered Vault database path links to metadata-only lifecycle detail; private cleanup handles are never returned. An export sink reference links Admin to durable event delivery. An export retry resends evidence only. See review/quorum, lifecycle, export and upgrade contracts.
