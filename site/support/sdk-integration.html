Build · execution ownership

SDK integrations

Keep your SDK's model loop in the app and ask for tool decisions, or move that loop into a Runkite runner and create managed Threads/Runs. Choose the boundary your caller needs. The frontend can remain in Next, Nuxt or another app.

Availability checked 2026-10-29. The latest published tag is v0.5.8. The decision API shipped in v0.5.3. The managed AI SDK runner ships in runkite-runner from v0.5.8 (optional peer ai@7.0.155). Repository helper guards and Microsoft function middleware remain unpublished as runkite-governance packages. See CHANGELOG before selecting a package version.

App-owned tool governance

A normal AI SDK tool.execute or a Microsoft local function can ask Runkite once before execution. Use a server-side key with the explicit governance:decide permission; read/write and agent-run permissions do not imply it. The key selects the tenant. Policy identities and the target arguments must come from trusted server code.

  1. Submit agent, connector, tool and exact arguments to /governance/decide.
  2. Execute only after allow. An allow is permission, not evidence that the tool executed.
  3. For pending, persist the action ID and original operation in the app, then return promptly.
  4. On a later authenticated request, poll GET /governance/actions/{action_id} and execute the saved operation only after approved.
  5. Reject fresh replacement arguments and use an application transaction, downstream idempotency key or outbox to prevent duplicate effects.

run_id on this door is a stable application correlation value, not a managed Runkite run or an execution-idempotency guarantee. Polling does not consume approval. Rejected or consumed actions must not execute. Embedded pending rows expire after 24 hours on SQL; expired rows cannot be approved. Admin approval updates the pending row and does not execute or resume your app.

The repository's TypeScript createGovernedExecute decides once and never polls or retries. It supports ordinary single-result JSON tools inside generateText and streamText; async-iterable tool outputs are outside that helper. The optional Python Microsoft GovernanceFunctionMiddleware uses the same door for local function tools, tested with agent-framework-core==1.23.0. It is not a Microsoft managed runner and creates no Admin run.

Managed Vercel AI SDK runs

The new TypeScript backend executes public AI SDK ToolLoopAgent code inside the runner. Your app creates a Runkite run and consumes its stream instead of calling the model loop in its HTTP handler. Runkite owns operational dispatch and records; the SDK still owns the model loop. No upstream fork, second scheduler, policy engine or SDK runtime inside the Go binary is needed. 

{
  "runner_kind": "typescript-ai-sdk",
  "graphs": { "managed_ai_sdk": "./agent.ts:createAgent" }
}

Each export is a per-run factory returning AiSdkAgentDefinition settings. The runner constructs the native SDK agent using those settings. This supported factory shape lets it supply trusted run context and check allowed_tools before local execution. An arbitrary opaque agent object is not automatically fully governable. 

# From a v0.5.8+ checkout or installed runkite-runner; no provider key for this example
cd typescript/runkite-runner
npm ci
npm run build
cd ../../examples/managed_ai_sdk
npm ci
cd ../..

# Local development plane, separate terminal
runkite dev --config examples/managed_ai_sdk/langgraph.json

# Matching runner
node typescript/runkite-runner/dist/cli.js --framework ai-sdk \
  --config examples/managed_ai_sdk/langgraph.json \
  --grpc-address localhost:50051 --http-address http://localhost:2026

ai@7.0.155 is the tested optional peer. The updated runner package exposes runkite-runner/ai-sdk. The example keeps the existing langgraph.json filename and graph mapping; the protocol does not require the agent to use LangGraph. For production, use the normal auth, runner-token, TLS and deployment profile.

Keep the AI SDK chat UI

AI SDK useChat reads its own UI message protocol. The example's app-side bridge converts the runner's custom:ai_sdk events through the SDK's public UI APIs and waits for durable Runkite completion before UI finish. Your existing app authenticates the user, checks chat ownership, maps chat IDs to server-owned threads, and keeps the Runkite key on the server. Use managed-run read/write permissions for that route; a governance-only key cannot create, read and cancel managed runs.

Only the new user text enters the runner. Browser history is presentation state and cannot replace its stored native model/tool history. A different attempt after rendering begins causes a delivery error rather than mixing two assistant replies. Automatic reconnect, regeneration and browser tool approvals are not part of this initial bridge.

Unreleased checkout bridge update: the app can explicitly detach delivery, reattach its owned run through an authenticated GET, and request run cancellation through a separate app POST. Create still cancels on disconnect by default; detach requires the app's persisted run ID. Reattach uses complete retained replay from the same attempt without dispatching the model or tools again. Persist the first assistant ID with onMessageStart before display and pass it back as expectedMessageId, so a replacement attempt cannot silently become a second assistant after reconnect. Missing history fails explicitly. This is manual reattachment, not an automatic retry loop; see the example's reconnect and Stop contract.

Durability and limits

  • Native successful-turn history uses the existing run-bound opaque checkpoint API, with framework/agent validation, exact generation and tenant binding, strong ETags and CAS.
  • State must commit before success. A committed current-run receipt replays after reclaim without repeating its model or tools. A crash before commit can still repeat external writes; downstream idempotency is required.
  • Initial scope is text and local JSON-result tools. No native approval/resume, client/provider tools, async-iterable tool outputs, binary attachments, time travel, partial-turn restore or whole-run caching.
  • Run lifecycle does not automatically govern every native tool body. Connector policy still requires the real connector path. Cancellation cannot undo an already completed effect.
  • Successful turns report provider tokens. The plane can settle cancellation before trailing usage arrives, so complete canceled-run spend is not guaranteed.
  • State is capped at 16 MiB, a turn's UI receipt at 8 MiB and final output at 3 MiB. The example bridge has its own documented request/frame limits.

make test-managed-ai-sdk exercises native SDK calls, the UI consumer and a real Go plane. Set RUNKITE_TEST_POSTGRES_DSN and RUNKITE_TEST_REDIS_URL together to select its Postgres + Redis profile, including crash-after-commit receipt replay without duplicate tool work or usage. This suite uses one plane process; it is not a multi-replica HA soak.
