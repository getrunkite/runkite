Langfuse traces

Send the plane and runner's existing operational spans to your Langfuse deployment through OpenTelemetry.

OTLP export already ships in v0.9.0. This current-checkout recipe adds setup guidance and qualification, not a Langfuse SDK, model proxy, database or UI inside Runkite. Langfuse runs separately.

Prepare a receiver

Use Langfuse's official self-hosting instructions and create a project. Configure its project API-key pair as OTLP Basic authorization through your deployment's process-secret mechanism. Runkite connector secret_ref does not configure the exporter.

The full trace endpoint is https://langfuse.example/api/public/otel/v1/traces. Replace the host and any reverse-proxy prefix with your own deployment. Langfuse accepts HTTP protobuf and JSON; Runkite's default gRPC selection will not work here. Keep TLS verification enabled outside a local fixture.

Configure each process

Have your deployment inject OTEL_EXPORTER_OTLP_TRACES_HEADERS with Authorization=Basic%20<encoded-project-key-pair>,x-langfuse-ingestion-version=4. The key pair is the project's public key, a colon, then its secret key, Base64-encoded without line wrapping. Use the standard OTLP header-value encoding. The v4 marker selects the current ingestion path. Keep actual credentials out of source and support messages.

Set the trace endpoint and a distinct service name on the plane and each runner container. Signal-specific configuration avoids constructing a trace path from a generic endpoint. Plane-only configuration does not configure independent runners.

Go plane:

OTEL_EXPORTER_OTLP_TRACES_ENDPOINT=https://langfuse.example/api/public/otel/v1/traces
OTEL_EXPORTER_OTLP_TRACES_PROTOCOL=http/protobuf
OTEL_SERVICE_NAME=runkite

Python runner: use the same endpoint with http/protobuf and a distinct service name such as runkite-runner-python. Install the runner's existing otel extra. If those optional packages are absent, Python logs a warning and tracing stays disabled.

TypeScript runner: use the same endpoint with http/json and a distinct service name such as runkite-runner-typescript. Its current HTTP exporter sends JSON even when the HTTP selector is labelled http/protobuf. Go and Python send protobuf. Use the actual per-language encoding when configuring a receiver or collector.

See the complete deployment recipe and Langfuse's official OTLP contract for headers and version-specific behavior.

Understand the observations

The plane creates a run span and supplies its W3C traceparent with the assignment. Runners create runkite.run beneath that context. Existing LangChain callbacks add model/tool name and status children. A name such as runkite.llm does not provide automatic prompt/completion, token or cost data for a Langfuse generation.

Run, thread and graph identifiers remain Runkite attributes. A Runkite thread is not automatically a Langfuse session, and a Runkite principal is not automatically a Langfuse user. An optional external collector mapping needs its own tested semantics. Additional framework instrumentation can export a different shape.

LOG_FORMAT=json controls stdout logs. Prometheus metrics remain separate too; do not send either to the traces URL. See the receiver's signal support.

Verify a deployment

  1. Use one synthetic run and distinct service names; no customer prompt or credential belongs in a diagnostic span.
  2. Allow batch delivery or graceful exporter shutdown. HTTP acceptance is not evidence of persisted asynchronous observations.
  3. Read the backend's supported API or UI. Verify trace ID, parent IDs, span names and expected run metadata across the plane and worker.
  4. Check run.status against durable Runkite state and confirm ordinary metadata has no invented body, token or cost data.
  5. Test rejected authorization without logging header values before adding collector transformations or more instrumentation.

Verified locally on November 17, 2026 against unmodified, self-hosted Langfuse v4.81.0 at f1e38efe36a752c551288292dc6318ce4c11ce1a: actual Go/Python/TypeScript exporters and production run-span/LangChain callback helpers persisted seven ordinary SPAN observations across three services in one connected trace, with the expected parents and metadata. Missing/invalid-auth read probes were denied. No generation or model call was produced; empty model and zero usage fields are backend placeholders. This proves the exporter/helper boundary, without plane dispatch, framework workers, business tool execution, providers, HA or UI qualification. The wire/offline workflow does not start Langfuse. See the reproduction commands, sanitized receipt and engineering note.

Keep the data boundary explicit

  • Names, IDs, exception text and application/framework-added attributes can contain sensitive data even though built-in callbacks omit normal bodies. Configure receiver access, retention and redaction before exporting production traces.
  • Langfuse project permissions do not inherit Runkite tenant permissions. A shared plane can emit multiple tenants into the selected project; choose an appropriate receiver/deployment boundary.
  • Tracing is best effort. Restart, replica takeover, abrupt shutdown or receiver failure can leave incomplete spans. The live plane span handle is process-local; durable run state remains authoritative.
  • A trace cannot authorize a tool, prove an exactly-once business effect or establish rollback after cancellation. Native tools still need to use an existing connector gate to receive its governance.
