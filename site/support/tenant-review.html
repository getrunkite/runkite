Govern

Tenant review

Give a reviewer access to their team's operations without making them a deployment-wide administrator.

Availability: v0.7.0 candidate source (not published). Published v0.6.1 binaries do not implement this workspace. Rebuild from the matching source; approval and evidence storage require Postgres, MySQL or SQLite.

Reviewer permissions are implemented in that source. Upgrading every HTTP replica is a rollout requirement: old binaries cannot recognize the new role strings. API-key/JWT/webhook providers already default to strict permissions unless explicitly overridden; the Helm example also sets them to true.

Start with the right access

Global Admin remains the place for deployment-wide operations. A tenant reviewer uses the separate /admin/review/ workspace. Its API takes the tenant from verified authentication, not an editable filter, URL or request header.

  • governance:read: inspect the tenant's approval metadata and recorded connector actions. Argument displays are omitted.
  • governance:approve: includes that read access, shows the existing capped/redacted argument display and permits approval or denial.
  • Neither permission allows policy/grant editing, break-glass, agent dispatch, conversations or another tenant's records.

These roles use the existing primary API-key, JWT or auth-webhook provider. They add no user directory. An identity and explicit tenant are required; set the tenant to default deliberately for a single-tenant deployment. Separate auth.admin_keys continue to serve global Admin and are not Review login credentials.

Configure a reviewer

Merge these entries into your existing authentication configuration. The strings below are placeholders, not usable deployment credentials. Keep your existing global Admin recovery access and runner authentication.

{
  "auth": {
    "type": "api_key",
    "strict_permissions": true,
    "keys": {
      "replace-with-read-only-key": {
        "name": "review-reader",
        "tenant_id": "acme",
        "permissions": ["governance:read"]
      },
      "replace-with-approver-key": {
        "name": "review-approver",
        "tenant_id": "acme",
        "permissions": ["governance:approve"]
      }
    }
  }
}

With JWT or webhook auth, map those permission strings and the actual verified identity/tenant through your existing provider. A missing JWT subject or webhook user identity cannot use a compatibility placeholder to obtain review access. Empty permissions never grant Review, even when compatibility strict_permissions: false is configured.

Upgrade every replica before issuing these permissions. Old binaries do not implement the boundary and may filter unknown role strings differently. Use strict permissions and activate reviewer grants only after the fleet is upgraded. Review sessions add no schema migration of their own, but the v0.7.0 candidate source (not published) includes security and target-binding migrations. Follow the target-binding maintenance procedure and the Review upgrade procedure first.

Review an operation

  1. Open $BASE/admin/review/ on your self-hosted plane and sign in with the primary reviewer credential. The credential is exchanged once and is not stored in browser storage.
  2. Confirm the displayed identity, tenant and access level. There is no tenant picker that can widen your scope.
  3. Open Approvals to inspect an operation. An approver sees the existing redacted argument display; a read-only reviewer sees metadata. Legacy or expired rows require fresh submission/review as described by the approval guide.
  4. Approve or deny only when your role allows it. The server enforces that rule even for hand-written HTTP requests. Approval records a decision; the caller still continues the exact operation.
  5. Use Evidence for managed connector attempts. A response is not business success. Investigate unknown outcomes in the downstream service before retrying.

Standalone app-owned decisions can appear in Approvals without a managed run. Their operation IDs do not imply a conversation exists. Review offers no conversation endpoint or run-detail navigation. Action evidence requires policy.action_evidence with required audit; approval review can be used independently on existing SQL pending actions.

Managed rows show their stored target revision. An approval belongs to that configured connector target as well as the original run and arguments, even when action capture is off. Missing or unsupported managed target bindings require fresh submission and review; Approve is disabled and Deny remains available. A changed current target returns 409. The display cannot confirm configuration across replicas or prove a remote tool implementation. Standalone expiring decisions remain app-owned and require no connector target. See target-bound approvals.

Sessions and sign-out

Review sessions have a fixed maximum lifetime of 15 minutes. Activity does not extend it. Expiry clears the workspace and requires fresh login. Roles are captured at login; changing an IdP grant does not instantly revoke an existing cookie. Logout or fixed expiry ends that session.

Review has its own httpOnly cookie, CSRF token and memory/Redis namespace. It cannot be moved into global Admin to gain authority. Admin and Review sessions are independent, including sign-out. A failed logout is shown as unconfirmed so you can restore session storage and retry.

Machine clients can send the primary Bearer/API key directly to /review-api. Cookie mutations require the matching CSRF token. Do not combine Bearer authentication and a browser cookie for logout; that request is refused. Bearer-only logout does not revoke the API key or JWT.

If access is refused

  • No provider configured: configure primary authentication. Review has no anonymous local/dev access; global Admin retains its existing local mode.
  • 403: check the explicit identity, tenant, role and CSRF token. Client read, write, agent-run and governance:decide permissions do not grant Review.
  • 404: the requested ID is missing or outside your tenant. Filters and cursors do not confer additional authority.
  • 409: current policy, expiry, status or approval binding prevents approval. A prior approval is not a permanent policy exception.
  • 501: use a SQL state backend, or implement the optional isolated Review-session capability if you supply a custom session store.

Keep bootstrap global Admin access for recovery and role configuration. Reviewers cannot assign themselves roles or edit policy. Subsequent unreleased review quorum and requester exclusion are now available, with configured policy and optional advertised-schema binding. Neither proves remote implementation. Review also reads own-tenant lease metadata but cannot renew/revoke.

Test the multi-replica boundary locally

From a source checkout with Go, Docker and Compose, run make test-review-ha. It creates disposable Postgres/Redis services and starts two real control-plane processes with strict authentication and a synthetic MCP target. It checks cross-replica sessions, tenant/role isolation, competing approval and dispatch, process loss, retained evidence and logout. It uses no paid model or cloud account.

For bounded repetition, run RUNKITE_TEST_REVIEW_REPETITIONS=3 make test-review-ha (1 through 20). Each cycle normally takes about a minute. The printed output directory contains a JSON report and sanitized process/fixture logs. Each database uses a generated per-run password; retained configuration contains its reference. The wrapper removes only its own infrastructure and ignores inherited database URLs and repository .env settings.

Use an isolated CI worker or firewall-protected workstation. Only database mappings are loopback-bound; the current CLI's HTTP/gRPC listeners can accept connections on other interfaces. This finite test does not qualify live model providers, database failover, arbitrary-code sandboxing or a long cloud soak.

API and engineering

Review uses /review-api/session, /review-api/pending-actions (list, detail, approve and deny), and /review-api/connector-actions (list and metadata detail). Lists are bounded to 100 records per page and use X-Next-Cursor. Detail and mutations stay tenant scoped. There is no general Audit, Threads, Runs, grant or secret-management API here.
