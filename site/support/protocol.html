Two protocols

Clients never speak Runner Protocol. Runners never expose Agent Protocol.

Agent Protocol (front door)

Threads, runs, streaming, the public, framework-agnostic client API. SDKs and HTTP clients live here. This is what product UIs and automations call.

Follow the LangGraph client walkthrough (Markdown on GitHub) to create a thread and stream a run with langgraph_sdk.get_client. The client calls the plane while a separate runner executes the graph.

  • Create thread → create run → wait or stream
  • Cancel; framework-native interrupt/resume when the adapter supports it
  • No knowledge of which runner pod holds the job

Runner Protocol (back door)

Runkite’s internal contract: pull job, stream events, heartbeat, reclaim/fencing. Workers authenticate with runner tokens and never publish a public Agent surface.

  • Dequeue assignment with generation / fencing token
  • Heartbeat; on superseded: true cancel local work
  • Report status / stream events with the exact assignment generation, including zero
  • Authenticated runner kind must match dequeue/watch requests and the run's assignment
  • Persist completion and finalize before queue Ack; delivery failure leaves recovery work

App-owned tool decisions

An app that keeps its model loop can instead call POST /governance/decide and poll GET /governance/actions/{action_id}. This HTTP policy boundary does not create a managed thread/run or dispatch a runner. The app executes the tool and owns pending continuation. It does not inherit run kill switches, break-glass or spend caps. See SDK integrations.

MCP clients and safe retries

Unreleased, current source: MCP discovery can describe structured agent input inside the existing input envelope when a usable stored report exists. Missing, unsupported, invalid or oversized reports keep the generic shape. Discovery is advisory: raw input is forwarded without defaults or coercion. Existing sessions retain their catalog; reconnect after report changes. Freshness remains unknown. See the supported subset and limits.

Runkite's public /mcp exposes configured agents as tools. Calling a tool creates a managed run through the same admission and runner path. This is separate from the outgoing run-bound connector proxy.

Available in v0.9.0: an optional run_id lets an MCP caller retry the same retained operation after losing a response. Published v0.8.0 does not implement this MCP retry contract. REST already supports client-selected run IDs.

{
  "message": "Summarize this document",
  "run_id": "document-summary-operation-123"
}

Confirm that tools/list advertises run_id before relying on retry protection; an older server may ignore an unknown argument. Generate and persist the operation ID in the calling app. A matching retry reuses the existing run and original thread; it does not enqueue another assignment. The agent, input and any explicitly supplied thread_id must match. Conflicting reuse returns a tool error. Omitting run_id retains the existing new-run behavior.

Calls still wait synchronously. A lost response is not evidence that execution stopped. Keep the same operation ID when reconnecting and use a new one only for genuinely new work. The stored run must remain available; deletion/pruning ends retry protection. This is not exactly-once external execution or an atomic transaction across the run store and queue. Failed, interrupted and timed-out runs remain tool errors.

The endpoint still needs its normal write/admin client credential. Retry observation checks agent authority too. See the MCP guide for authentication, sticky routing, retention and the existing REST background-run alternative.

A Trinity caller example

Checkout example in v0.9.0 source: the specialist example keeps a Trinity agent's native loop and invokes one Runkite-managed specialist through an explicitly installed stdio MCP caller. It saves the caller's intent before dispatch, then observes retries through existing REST get/wait routes without another tool invocation. Only the specialist appears as a managed Runkite run. The surrounding Trinity conversation and its other tools stay outside that run. This example is not a separately published package.

The guide separates pinned Trinity configuration checks, real Runkite API/runner protocol qualification and native Trinity runtime execution. Native Trinity execution remains unqualified, and these checks do not establish upstream endorsement. See the engineering boundary for authority, destination restrictions and retention limits.

Why not one protocol

Collapsing them either leaks reclaim/fencing internals to every client, or starves workers of the semantics they need to fail closed under partition. Keep the seam.
