Ecosystem integrations

Connect Runkite to your stack.

Keep the tools your team already uses. Run agents from your preferred framework, call a specialist from another app, test its answers, or follow its traces in your own observability backend.

Choose the job you need below. Each guide explains who owns execution, how to connect, and what was tested. Runkite stays self-hosted; the other project keeps its own application, runtime and storage.

Run agents Call specialists Evaluate answers Connect chat Export traces Route models

Start with one working connection.

  1. Choose the execution boundary. For caller and chat integrations, first complete a local echo run. If your application keeps its model loop, use tool decisions instead of moving the whole app.
  2. Follow one setup guide. It identifies the package, checkout example or external service you need. Keep plane credentials in a trusted backend and give the caller only the required authority.
  3. Verify your deployment. Run the guide's smoke or qualification command. Inspect the matching managed run in Admin, or confirm trace persistence in the receiver. Add your own agent, model and infrastructure after that first success.

Find the connection that fits your use case.

What the labels mean: published runner profiles are installed from packages. Checkout examples are application code you copy or adapt from the source. Configuration recipes connect existing protocol support. Experimental fixtures qualify a narrower boundary. Upgrading Runkite does not install every example.

Published runner profiles

Run your framework through Runkite.

LangGraph / LangGraph.js · Vercel AI SDK · Microsoft Agent Framework · OpenAI Agents SDK · Pydantic AI · Google ADK

Your app creates a managed thread and run. A separate Python or TypeScript runner executes the SDK's model loop while Runkite handles admission, dispatch, durable run records and operational controls.

Use the profile matrix for supported tools, conversation state and resume limits. Local tools receive connector policy only when they call through the connector path.

Checkout caller examples

Call one specialist from another agent.

Langflow · Trinity · MCP clients

Keep the surrounding conversation and model loop in the caller. Invoke a configured Runkite agent through the public /mcp interface, creating an ordinary managed run for that specialist.

Langflow's pinned headless client is qualified, not its complete visual-editor experience. Trinity's bridge and source configuration are tested; a full native Trinity deployment remains unqualified. Preserve operation intent before retrying.

Checkout evaluation provider

Test an agent before changing it.

promptfoo

Rerun known questions after a prompt, model or agent change. The provider submits each intentional evaluation as a Runkite-managed run, waits for the durable result, and returns the answer to promptfoo's assertions. Inspect the execution in Admin when a test fails.

The native CLI path is qualified with a scripted worker. The bundled test is a smoke test, not an adversarial security suite. Automated red-team strategies and checks proving connector denials or actual tool side effects are not qualified.

Checkout application bridges

Keep your chat UI. Use managed runs.

AI SDK UI · Next / Nuxt · AG-UI

Connect an authenticated application route to Runkite-managed execution. Stream text to your existing interface, detach and reattach to a retained run, and expose an explicit Stop action.

Your app owns authentication, chat history and run ownership. AG-UI is a plain-text transport slice, not complete tool, interrupt or multimodal support and not a qualified CopilotKit widget.

OTLP configuration recipe

Follow execution in your trace backend.

Langfuse · OpenTelemetry receivers

Point the existing plane and runner exporters at your receiver. The Langfuse guide covers authentication, HTTP encoding and verifying that operational spans actually persist in a separately deployed backend.

A real Langfuse receiver was qualified. The path does not automatically record prompt bodies or populate generation, cost, score or user/session mappings. Logs remain separate from traces.

Published external walkthrough

Choose models behind the agent's SDK.

vLLM Semantic Router

Run an AI SDK agent through Runkite and point the runner's OpenAI-compatible model client at Semantic Router. The router selects among your configured model backends while Runkite manages the agent run.

The model request travels from the runner to Semantic Router. Runkite does not proxy model traffic or choose models. The runnable example lives in the published walkthrough, outside this repository.

More connections through existing protocols.

These are configuration recipes with their own validation scope, separate from the native application qualifications above.

  • Cline over MCP: configure Streamable HTTP and a dedicated caller key to expose authorized Runkite agents as tools.
  • Deep Agents through LangGraph: load the compiled graph with the existing runner. Native subagents do not automatically become separate plane runs.
  • Phoenix over OTLP: configure existing exporters and verify a connected trace in your own receiver. No Phoenix-specific native qualification is claimed.
  • GitHub MCP Server as a connector: keep the server external and use Runkite's outbound connector gate, grants and credential injection. Protocol tests do not establish live GitHub-service qualification.

Experimental execution fixture

OpenShell: qualify an external boundary.

The checkout includes an external OpenShell workload and an effective-policy checker fixture. This is separate from ordinary framework runners. It does not automatically sandbox them or add a production enforcement gate.

Understand the tested policy boundary and use the linked engineering qualification commands before experimenting.

What these integrations establish.

Each connection uses an existing public boundary: a runner, REST, MCP, chat transport or OTLP. The linked guides record the pinned versions and tests. A qualified slice does not establish support for every upstream feature, production adoption or a partnership.

For implementation and test evidence, see the source integration guide and engineering and qualification map. Missing an integration? Describe your caller and the operation it needs.
