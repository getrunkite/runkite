Identity, delegation and usage

Connect an agent operation to its requesting identity, authenticated worker and external credential audit.

Next release preview: these additions follow v0.7.0 and are not in its published artifacts. Build matching current plane and runner source for evaluation. Governance helper publication and independent external assessment remain separately verified gates.

Maintenance upgrade: back up, drain all runners and writers, apply Postgres/SQLite migration 22 or MySQL migration 23, and replace every replica before enabling strict ownership. Mixed old/new writers are unsupported. Follow the operator upgrade guide and usage design and rollout.

Four identities with different responsibilities

The requesting user, configured agent, worker holding an attempt and downstream delegated actor are distinct. Runkite keeps their evidence separate. Your identity provider issues identities, Vault issues secrets, and Runkite binds governed operations to current authority.

Strict admission JWT validation requires issuer, audience, expiry and subject. It records bounded issuer-asserted actor context. A historical admission record does not prove a credential is still valid or that an actor possessed a key.

Bind the worker to its assignment

Runner upgrade: when a client certificate is configured, runner HTTP calls require HTTPS, even with the new workload profile off. Update plaintext checkpoint, connector and status URLs before upgrading those runners.

The opt-in mTLS workload profile uses an externally issued client certificate, an exact URI-to-kind or pool allowlist, and its public-key fingerprint. Another holder of the same fleet token cannot renew, report events or complete that worker's owned attempt.

Deploy direct verified TLS on both plane listeners, matching client certificate settings for gRPC and HTTP, SQL state and a supported in-process or Redis queue. NATS and Kafka are refused in this strict profile. Certificate rotation drains or reclaims existing attempts. Retiring a public key requires updating the operator file and replacing all HTTP/gRPC replicas; no immediate external-CA revocation or hostile-code attestation is claimed.

Workload setup and rotation · Design and trust boundary

The strict listener requires trusted client certificates for direct Admin/API access too. Public ingress can use its own upstream certificate and forward public routes only, while internal runner routes stay private. Forwarded identity headers are not worker proof. Read the deployment boundary before enabling the profile.

Constrain existing token exchange

Constrained exchange requires JWT admission with both strict_identity: true and forward_token: true, plus the registered connector contract. Existing sessions with only legacy token fields need fresh admission.

Runkite already supports RFC 8693 token exchange. An optional registered contract adds audiences, resources, explicit scopes, a maximum TTL and an external actor assertion reference. The constrained path derives the subject assertion from the trusted run assignment and refuses a worker's replacement user token.

The issuer and resource server still validate and enforce actual token authority. These are bearer exchanges; they do not establish DPoP or a universal cryptographic delegation chain. Ordinary deployments keep existing behavior unless they enable the new contract.

Follow one operation across systems

Admin and tenant Review display recorded admission and worker identity alongside the action's policy, target, approval and dispatch evidence. Credential metadata includes safe Vault issuance and latest renewal request IDs when known. Final action exports retain the issuance ID.

Operator-enabled MCP correlation headers can carry the public action and credential references to a participating downstream service. The same references reach Vault operations. Join those facts in your existing collector or SIEM, preserving credential redaction and event deduplication.

A Vault request establishes a Vault interaction; a proxy response establishes an observed response. Business success requires resource-side evidence. Calls outside Runkite's paths need external observation.

Keep unknown usage different from zero

The experimental external JSONL workload contract gains cumulative, sequenced usage reports. The trusted worker acknowledges a report after durable SQL commit. Completion or cancellation settles the latest acknowledged snapshot, and receipt replay preserves its original submitting worker.

Admin Run Detail distinguishes unavailable usage, partial reports and workload-declared completion. A reported zero is retained explicitly. Missing USD remains unreported. These measurements are workload claims, so provider accounting and limits remain necessary for trusted billing or hostile-workload hard caps.

Evaluate the actual deployment

Maintainer tests and bounded disposable HA/TLS scenarios are reproducible evidence for their stated cases. They are not an independent security assessment, every-provider qualification or a global security ranking. The external runtime bridge remains experimental.
