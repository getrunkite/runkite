Security

Four layers, stacked: who can talk to the plane at all, who can run which agent, which connectors an agent may call, and records of policy decisions. This page explains each layer and, importantly, where the edges of what the plane can see and enforce actually are.

Layer 1, can you talk to the plane at all?

Protected API requests need a credential (an API key or JWT) unless you've deliberately left auth off for local development. Each credential carries one or more permissions. read, write, or admin: and every route requires a specific one. A client key with only read cannot create a run; a key without admin cannot open the Admin dashboard, full stop, regardless of how much it can otherwise do. See Admin login for the exact config shape.

The v0.6.0 auth webhook hardening keys cached results by the method, path and all forwarded header data, including cookies and custom identity headers. It honors request cancellation, refuses redirects and requires a successful HTTP status with one complete JSON response capped at 1 MiB. Configure the provider's final URL and see webhook authentication for the response contract.

Layer 2, can this credential run this agent?

By default, a valid client credential with write can create a run against any agent. If you need finer control than that, "this key may only run the support-bot agent, not the finance one", add an agents:<id>:run grant to that key's permissions. This only applies to the run-create routes, not cancel/delete/store access, which still fall back to the plain read/write check.

Layer 3, can this agent call this external service?

This is the connector policy layer, covered in full on Connectors & HITL. Short version: a connector call under default-deny policy needs a matching grant (static in config, or created live in Admin). Operators can explicitly configure a different default effect. You can force specific tools to require human approval regardless of the grant. Policy auditing writes decisions to SQL, searchable from Admin → Audit. Best-effort auditing does not guarantee a saved row during a storage failure. Current unreleased source adds policy.audit_required to require durable decisions before protected access. Published v0.6.1 does not implement that mode. See audit and action evidence.

Where fail-closed applies

Authentication, permissions and shared session lookup failures refuse access. A failed policy audit write blocks protected access only when the unreleased required-audit mode is configured; best-effort audit does not supply that guarantee. In production mode, serve refuses to even start with an insecure combination (e.g. runner tokens configured but no matching tenant allow-list) rather than booting into a state that looks secure but isn't. See Why fail-closed for the reasoning.

Process isolation is a separate boundary

Connector policy and runner tool allowlists do not sandbox arbitrary code. Direct file access and network calls outside those hooks remain the operator's responsibility. The Helm defaults already use a non-root identity, dropped capabilities and disabled privilege escalation. The chart's optional network policies restrict ingress, not runner egress. Use an external execution sandbox when untrusted code needs stronger confinement.

OpenShell is a candidate for that boundary, not an available Runkite integration. Putting the whole worker in a sandbox does not by itself hide its runner token from in-process agent code. The execution-boundary rationale describes the trusted worker, isolated agent and evidence needed before we can claim compatibility.

v0.6.0 NATS partition guard: a run ID is a literal partition, not a subject filter. Queue, stream and cancel paths reject wildcards and unsupported JetStream keys, and consumers verify the exact received subject. Valid subject/key layouts are unchanged. See the Compatible NATS upgrade boundary; Postgres/Redis does not share this transport-specific ID restriction.

Authenticated dispatch verifies the actual dequeued job's kind before attempt advancement or input delivery, returning a misroute with a generation-bearing Nack. NATS consumer creation rejects a conflicting filter when kind names collide after dot-to-underscore conversion. See operator reconciliation guidance. Trusted no-token local mode remains unchanged.

v0.6.0 exact runtime identities

The runner and plane preserve nonempty tenant/run identities exactly. Unicode or legacy header-unsafe identities use unpadded base64url UTF-8 in X-Runkite-Run-Id-B64 or X-Runkite-Tenant-Id-B64, omitting the corresponding raw header. Upgrade the plane before those helpers. Bound proxy authority still comes from the active assignment; a tenant claim cannot replace it. Mixed, duplicate or malformed representations of the identity used by a route are rejected. New run IDs with controls or outer whitespace return HTTP 400; stored legacy IDs are not renamed.

Tenancy, what "multi-tenant" means here today

Every resource (agent, thread, run) carries a flat tenant_id: this is isolation by a tag on each row, not a full organization/team/workspace hierarchy with its own nested permissions. Plane-managed state and opaque checkpoints carry tenant binding. v0.6.0 direct Postgres LangGraph is limited to guarded default-tenant thread IDs; named tenants require HTTP proxy checkpoints because legacy prefixed rows have no trusted ownership attestation. If you're using runner tokens (multiple runner fleets sharing one control plane), you must also configure RUNNER_TENANTS_<kind> per runner kind, see Multi-tenant keys for the full setup and what happens if you skip it (the plane refuses to boot rather than silently trusting an unbound tenant claim).

Child mutations now hold exact parent-tenant ownership through the transaction. Mongo deletes the parent and that tenant's children atomically. Native LangGraph direct checkpoints refuse every named tenant, while fresh memory keeps its delimiter guard. Default-tenant colon thread IDs also need proxy mode. Existing named direct history requires explicit ownership resolution. See the checkpoint boundary and upgrade instructions before continuing affected histories. Previously mixed native data is not repaired automatically.

v0.6.0 MySQL identity fix: schema v17 replaces the default case/accent-insensitive behavior on identity and security columns with utf8mb4_0900_bin NO PAD. Case, accent, Unicode-spelling and trailing-space differences no longer identify the same tenant or security key. Display/search text keeps its intended search behavior. MySQL remains Compatible, and the migration cannot repair already-overwritten identities. Existing databases require a verified backup, all old writers stopped and a maintenance window. Preflight rejects aliased foreign-key IDs and cross-tenant child ownership before DDL. These failures and unsupported collation must be explicitly repaired, never bypassed; downgrade is refused. Follow the MySQL upgrade procedure.

What the plane stores and where control stops

The plane persists managed run input/output, thread values, published events and opaque checkpoints. Those payloads can contain prompts, model replies and tool results; restrict read access and configure retention accordingly. Opaque means the plane does not interpret a framework's checkpoint schema, not that its bytes are absent from storage.

Built-in OTLP spans export run/model/tool metadata without automatic full-body prompt/completion capture. Point OTEL_EXPORTER_OTLP_ENDPOINT at your chosen collector or backend; logs remain on stdout, with LOG_FORMAT=json configured separately. Add deliberate SDK instrumentation if richer trace content is required. Connector policy covers calls that pass through its gate. Code using independently supplied credentials or an unguarded local tool remains outside that execution boundary.

Connector action evidence (unreleased)

Current source after v0.6.1 adds an opt-in SQL trail for managed MCP tool attempts. Review the original policy decision, final approval or break-glass authority, dispatch intent and observed response in Admin. A response is not proof of a business effect; an unknown outcome may have executed. This records metadata and adds no credential vault or secret leases. See Connector actions for configuration, fresh-review requirements, investigation and retention.

Managed approvals now bind both the original stored run incarnation and the configured connector target, even without evidence capture. A versioned SHA-256 descriptor includes endpoint, transport, auth identity/reference, scopes, filters and optional nonsecret mcp.revision; resolved credentials are excluded. Dispatch uses the configuration snapshot whose revision was evaluated. This does not attest remote tool code, discover schema changes, pin a policy revision or identify the resolved credential version. Historical unbound approvals require fresh review. See target-bound approvals and the upgrade procedure.

Tenant Review workspace (unreleased)

Current source after v0.6.1 adds primary governance:read and governance:approve roles for a verified tenant. Reviewers use a separate workspace and API; they gain no global Admin or conversation access. Read-only metadata excludes argument displays, while approvers keep the existing redacted review view. See Tenant review for setup, absolute session expiry, API scope and rollout.
